# 玩家角色控制（状态机实现）

> 本文只写**已经做出来的东西**：玩家能做什么、代码怎么实现的、为什么采用这种设计。
> 手感数值和键位都会变，本文不写死它们，只指出在哪个表里；具体数值以
> `Assets/Resources/Content/data/*.json` 为准（`tools/verify-content.ps1` 会校验）。
>
> 适用版本：2026-11-16（八向走位版，无重力、无跳跃）。角色：Blitz（Spine 骨骼动画）。

## 1. 玩家现在能做什么

| 动作 | 默认按键 | 触发条件 | 结果 |
| --- | --- | --- | --- |
| 左右移动 | `A` / `D` | 水平输入超过死区 | 以 `moveSpeed` 左右移动，朝移动方向自动转身 |
| 纵深移动 | `W` / `S` | 纵深输入超过死区 | 以 `moveSpeedY` 在画面里上下走（不是跳，是「靠近/远离镜头」） |
| 冲刺 | `LeftShift` / `Space` | 冷却结束 + 任一冲刺键按下的那一帧 | 朝当前朝向以 `dashDistance / dashDuration` 的速度水平冲 `dashDuration` 秒，纵深速度清零 |
| 射击（连射） | 鼠标左键按住 | `Attack_Loop` 动画的 `OnAttack` 事件 | 每次事件出一发特殊弹；松开后收枪。不瞄准时朝面朝方向平射 |
| 瞄准 | 鼠标右键按住 | `AimHeld` 为真 | 屏幕上出现白色圆环准星（中心一个点）并跟随鼠标；此时射击朝准星指的世界点飞（仰角不超过 `aimMaxAngle`），开火瞬间身体转向准星那一侧 |
| 近战 | `F` | 按下的那一帧 | 播 `Skill_02` 单次动画，期间原地不动；动画中段在身前判定一次盒子，命中 `Enemy` 标签的目标造成 `meleeDamage` 伤害 |

按键不是写死在代码里的，来自 `Content/data/input.json`；上表的默认值就是该文件的初始内容。

### 「上下移动」是什么

场景是一整幅桥面全景插画，不是横版剖面。角色能在这幅画上**沿桥面往远处/近处走**，
但始终站在同一块桥面上——所以：

- 刚体**没有重力**（`gravityScale = 0`），不会往下掉；
- **没有跳跃**，`W/S` 改变的是画面里的纵深位置，不是高度；
- 角色被夹在背景图上那条带状区域里：横向铺满整张地图（背景块并集），纵向由 `arena.json` 的比例限定，走不出去。

### 没有做的（避免误会）

- 玩家没有受击、硬直、死亡状态；
- 没有跳跃、没有高度维度（见上一节）；
- 没有冲刺残影 / 瞬移特效（冲刺只是改速度 + 播 `Move` 动画）；
- 没有移动端触屏操作（见 `Documents/拍板记录.md` 的「待决定」）。

## 2. 结构：谁负责什么

一次「按下 A 键」要经过三层，各层边界是编译期强制的（三个 asmdef）：

| 层 | 位置 | 职责 | 相关的内容 |
| --- | --- | --- | --- |
| Core（纯 C#，不引用 UnityEngine） | `Assets/Scripts/Core/` | 数值 DTO + 纯逻辑规则 | `PlayerTuning`（手感）、`ArenaTuning`（活动范围）、`DashCooldown`（冷却计时）、`Health`（标靶用） |
| Framework | `Assets/Scripts/Framework/` | 读内容表、存档 | `ContentLoader`（`Resources.Load` + LitJson） |
| Game | `Assets/Scripts/Game/` | 把数值接到引擎对象上 | `PlayerController`、`PlayerInputReader`、5 个状态、`ArenaBounds`、Spine 封装、枪口 |

数据流：

```
player.json / input.json / arena.json / assets.json
        │  ContentLoader（懒加载一次，缓存进 GameContent）
        ▼
PlayerTuning / InputTuning / ArenaTuning / SpineAnimations
        │
        ├──► PlayerInputReader.Poll()      每帧把设备状态变成「轴 / 按住 / 刚按下」
        ├──► ArenaBounds                   收集背景块 → 横向并集 + 纵向比例 → 世界矩形
        └──► PlayerController.Tuning       状态里读数值
                    │
                    ▼
             StateMachine.Tick()  ──► 当前状态决定「要不要换状态」「怎么动」
                    │
                    ▼
        Rigidbody2D.velocity / Spine 动画 / 枪口位置
                    │
                    ▼
        PlayerController.ClampToArena()  每物理帧最后夹一次活动范围
```

关键点：**状态里没有一个写死的数字**。`0.01` 这类纯数学保护量（除零下限、向量比较 epsilon）留在代码里并写注释，不算可调数值——这条是 `AGENTS.md` 硬约定的边界。

## 3. 状态机骨架

三个文件撑起整个骨架，它们在 `Assets/Scripts/Game/Player/States/`：

### 3.1 `IState`：四个生命周期方法

```csharp
void Enter();       // 进入时：播动画、给初速度、清零计时
void Tick();        // 每渲染帧：读输入、判断要不要换状态
void FixedTick();   // 每物理帧：改刚体速度
void Exit();        // 离开时：收尾（停速度、退订动画事件）
```

拆成 `Tick` 和 `FixedTick` 是有原因的两个时钟：

- **改速度必须在 `FixedUpdate` 里做**，否则物理帧率与渲染帧率不一致时移动距离会抖；
- **读输入、判断状态切换要跟着渲染帧走**，否则 30fps 机器上连点会被吞。
- `PlayerController` 里 `Update()` 调 `_machine.Tick()`，`FixedUpdate()` 先调 `_machine.FixedTick()`，**最后**再 `ClampToArena()`——夹范围放在状态机之后，任何状态改完速度都逃不掉这一次约束。

### 3.2 `StateMachine`：只做三件事

```csharp
public IState Current { get; private set; }
public IState Previous { get; private set; }
public void ChangeState(IState next, bool force = false)  // null 忽略、同一状态忽略（除非 force）
```

它**不**维护转移表，也**不**知道状态之间怎么走。切换条件写在每个状态自己的 `Tick()` 里：

```csharp
// PlayerIdleState.Tick()
if (inputs.DashPressed && Player.CanDash) { Machine.ChangeState(Player.DashState); return; }
if (inputs.MeleePressed) { Machine.ChangeState(Player.MeleeState); return; }
if (inputs.AttackPressed) { Machine.ChangeState(Player.AttackState); return; }
if (Player.HasMoveInput) Machine.ChangeState(Player.MoveState);
```

**为什么这样设计（状态自治）**：

1. **新增一个状态只需要改两处**：新建一个类 + 在相关状态的 `Tick` 里加一条 `if`。不用回头维护一张巨大的转移表，也不会出现「表里漏写一条边导致某状态进得去出不来」。
2. **每个状态的完整行为在一个文件里读得完**：什么时候进、进来播什么动画、每帧怎么动、什么时候走，全部相邻。排查「为什么冲刺时不能开枪」只要看 `PlayerDashState.cs`。
3. **代价是知识分散**：同一个输入在 Idle / Move 里各判一次，改优先级要动多个文件。目前只有 5 个状态、每处 3~5 行，这个代价可以接受；如果状态数上到十几个，再考虑把「优先级」抽成一张表。

`ChangeState` 忽略重复切换是刻意的：`Tick` 里每帧都可能满足同一条条件，重复 `Enter` 会反复重播动画、反复给初速度。真正需要「原地重来」的地方只有两处，都显式传了 `force`：

- `PlayerController.Start()` 强制进 `IdleState`（第一次进入没有 Previous）；
- 射击收枪期间再按扳机 → `ChangeState(Player.AttackState, true)`，重播 `Attack_Begin` 保证连点手感。

### 3.3 `PlayerState`：缓存两个引用

```csharp
protected readonly PlayerController Player;
protected readonly StateMachine Machine;
```

状态是**普通 C# 类**，不是 MonoBehaviour：它们不挂在 GameObject 上，由 `PlayerController.Awake()` 一次性 `new` 出来并缓存到 `IdleState`/`MoveState`/… 属性里。
这样做的原因是：状态本身没有引擎生命周期需求（不需要 `Update`，由控制器统一驱动），做成 MonoBehaviour 会多出 5 个组件、多一层执行顺序问题，还没法在编辑器里单看一个状态的行为。

## 4. 五个状态逐个说

### 4.1 Idle（待机）

- **进入**：播 `Idle` 循环；
- **每帧**：按固定优先级检查冲刺 → 近战 → 射击 → 移动；
- **物理帧**：`Move(Vector2.zero, 1f)`，把水平与纵深速度都压成 0（不是直接置 0，走同一条速度通道，避免与其他状态的速度写法不一致）。

为什么优先级是「冲刺 > 近战 > 射击 > 移动」：越「不可打断/位移性强」的动作越靠前。冲刺优先级最高是因为它有冷却、玩家按下就期待立刻位移；移动放最后，因为它是「默认动作」，前面都没触发才走。

### 4.2 Move（移动）

- **进入**：播 `Move` 循环；
- **每帧**：与 Idle 同样的优先级，另外「输入回到死区内」→ 回 Idle，否则 `FaceTo(MoveAxis)`；
- **物理帧**：`Move(Inputs.Axis2D, 1f)`。

`Axis2D` 是 `(MoveAxis, DepthAxis)` 的合成向量：`W` 给 `+1`、`S` 给 `-1`，斜着走时两轴同时有值，速度是两条轴各自算完相加，所以**斜向会比直向快约 1.4 倍**。这是当前取舍（两轴都不归一化），因为桥面走位时斜着走快一点反而更接近「抄近路」的直觉；要改成等速，只需在 `Move` 里归一化 `axis`——但那会同时改变所有方向的手感，属于要试玩确认的事（见 `Documents/拍板记录.md`「建议」）。

### 4.3 Dash（冲刺）

- **进入**：播 `Move` 动画（无专用冲刺动作），`Player.BeginDash()` → 启动冷却 + 立刻施加一次冲刺速度，`_elapsed = 0`；
- **每帧**：累加 `_elapsed`，到 `DashDuration` 后按输入回 Move/Idle；
- **物理帧**：`ApplyDashVelocity()`，**每物理帧重写**水平速度为 `Facing * DashSpeed`、纵深速度清零。原因：摩擦力、之前的惯性、碰撞后的速度衰减都会污染冲刺距离；每帧硬写才能保证 `dashDistance` 真的等于「速度 × 时间」；
- **退出**：`StopMovement()`，避免冲刺速度残留成走路速度。

冲刺期间**锁定方向与输入**：不读移动输入、不转身、不能开枪、不能近战。玩家在 0.2 秒里按别的键一律忽略——这是「位移型动作」的常规处理，否则会出现冲刺中途反向的鬼畜画面。

冲刺**只走水平**：纵深速度被清零，因为画面里「往前冲」在纵向上没有对应的位移方向，硬加会让角色斜着飘出桥面。

### 4.4 Attack（射击）

动画三段：`Attack_Begin`（抬枪）→ `Attack_Loop`（循环）→ `Attack_End`（收枪）。

- **进入**：`StopMovement()`（射击原地不动），订阅 `SpineAnimationPlayer.SpineEvent`，播 `Attack_Begin` 并 `Queue` `Attack_Loop`；清 `_hasFired` / `_finishing`；
- **每帧**：允许原地转身（子弹跟着枪口方向走，但不产生位移）；**射速完全由动画事件决定**：

  ```csharp
  private void OnSpineEvent(string animationName, string eventName)
  {
      if (_finishing) return;
      if (animationName != PlayerAnimations.AttackLoop) return;
      if (eventName != PlayerAnimations.AttackEvent) return;   // "OnAttack"

      _hasFired = true;
      Player.FireSpecial();
  }
  ```

  即：`Attack_Loop` 每循环一次、动画里的 `OnAttack` 事件触发一次 → 出一发。**不是每帧开火，也不是固定计时器**。好处是「射速」这个手感参数天然跟着动画走：改动画时长或换动画，射速自动跟着变，不会出现「动画慢吞吞、子弹却泼水」的脱节。
- **松开扳机**：`_hasFired && !AttackHeld` → 播 `Attack_End`，用 `GetDuration(Attack_End)` 当收枪计时，结束时回 Move/Idle；
- **短点击的边界**：如果松手时还一发都没出（点击快于 `Attack_Begin`），不立刻收枪，而是等第一次 `OnAttack` 出弹后再收。否则「快速点一下」会变成完全不放枪；
- **收枪期间再按**：`ChangeState(AttackState, true)` 重新进入，连点不会卡在收枪动画里；
- **退出**：退订动画事件（`_subscribed` 标志防重复订阅）。

为什么用事件而不是 `if (timer >= interval) Fire()`：一是上面说的与动画同步；二是「枪口火光」也挂在同一个事件上（见第 7 节），射击的视觉与判定来自同一个事实，不会各算各的。

### 4.5 Melee（近战）

- **进入**：`StopMovement()`，播 `Skill_02`（单次），`_duration = max(GetDuration(Skill_02), 0.1f)`，并把判定计时器设成 `min(meleeHitDelay, _duration * 0.6f)`；
- **每帧**：先推进判定计时器，到点就 `Player.MeleeStrike()` **一次**（`_struck` 标志保证一次挥击只判定一次）；再计时到 `_duration` → 按输入回 Move/Idle；
- **物理帧**：持续 `StopMovement()`，期间完全锁死（不响应移动、冲刺、射击）。

判定不在按下那一刻，而是等 `meleeHitDelay`（默认 0.12 秒）——刀落下来和掉血对齐。这个值会被夹到动画时长的 60% 以内，所以动画再短也一定挥得出这一下（夹取属于保护逻辑，写在代码里并注释，不进 JSON）。

`MeleeStrike()` 在 `PlayerController` 里，做的事就三件：按 `Facing` 算出身前一个盒子（长 `meleeRange`、高取 0.9 倍、从脚下抬 0.35 倍），用 `Physics2D.OverlapBoxAll` 取重叠碰撞体，筛出标签为 `Enemy` 的、按 `IDamageable` 去重后各结算一次 `meleeDamage`。

为什么是「一次性盒子」而不是「动画里挂个常驻攻击盒」：

- 一次挥击只应该掉一次血，盒子常驻会让多帧都命中；
- 判定范围由 `meleeRange` 一个数推导（高度、抬升都是比例），调手感只改一个值；
- 结算走 `IDamageable`——靶子和敌人共用同一套，不必为近战单独写一套伤害。

`Mathf.Max(..., 0.1f)` 是保护量：动画时长读不到（资源改名/动画缺失）时至少锁 0.1 秒，避免同一帧内进出造成死循环。

> 注意：因为**没有跳跃**，`Melee`/`Attack` 期间不存在「落地」问题，锁定就是纯锁定。

## 5. 状态转移图

```
                    ┌──────────────────────────────┐
                    │             Idle             │
                    └──┬────┬────┬──────┬──────────┘
         冲刺(冷却好)   │    │近战│ 射击  │ 有移动输入
                        ▼    ▼    ▼      ▼
                    ┌──────┐┌────┐┌──────┐┌──────┐
                    │ Dash ││Melee││Attack││ Move │
                    └──┬───┘└─┬──┘└──┬───┘└──┬───┘
                       │      │      │       │
         到时长→Move/Idle│  到时长→│  松手→收枪→│  松键→Idle（移动时继续 Move）
                       ▼      ▼      ▼       ▼
                    （全部可回 Idle 或 Move）

    Move ──DashPressed / 近战 / 射击──► 对应状态
    Dash ──到 DashDuration──► Move / Idle
    Attack ──松手且已出弹──► Attack_End 计时 ──► Move / Idle
```

用文字说清优先级（同一帧多个输入同时按下时，先命中的生效，后面的丢掉）：

| 当前状态 | 判定顺序 |
| --- | --- |
| Idle / Move | 冲刺 → 近战 → 射击 →（Move 额外：无输入回 Idle） |
| Dash | 计时结束 → Move / Idle |
| Attack | 收枪中再按 → 重进 Attack；松手 → 收枪 → Move / Idle |
| Melee | 计时结束 → Move / Idle |

## 6. 输入层：为什么是「轮询」而不是事件回调

`PlayerInputReader` 基于 **Input System Package**（`Keyboard.current` / `Mouse.current`），由 `PlayerController.Update()` 每帧调一次 `Poll()`。

```csharp
public void Poll()
{
    var previousDashHeld = _dashHeld;                 // 先存上一帧
    ...
    _dashHeld = InputBindings.IsHeld(keyboard, _bindings.dash);
    _dashPressed = _dashHeld && !previousDashHeld;    // 边沿自己算
}
```

三个设计决定：

1. **轮询而不是 `PlayerInput` 的 `SendMessage`/回调**：状态机需要一个「这一帧的事实快照」——`Axis2D`、`AttackHeld`、`DashPressed` 必须来自同一帧，各状态读到的值才一致。回调方式下，事件在别的时机进来，改的是同一个字段，很难保证「一帧内不变」；而且回调要配 Action Asset，键位就跑到 `.inputactions` 里去了，与「键位进 JSON」冲突。
2. **边沿（`Pressed`）自己算**：Input System 有 `wasPressedThisFrame`，但它与 `Poll()` 的调用时机耦合（同一帧多调一次就变成 false）。自己存上一帧状态最稳，也让调试覆盖（下面）走完全相同的路径。
3. **键位解析拆到 `InputBindings`**：`PlayerInputReader` 只做「读」，`InputBindings` 做「字符串 → `Key` / `MouseButton?`」。这样换键是纯数据操作（改 `input.json`），解析失败时退回默认键并 `Debug.LogError`，不会一改表就崩。

纵深轴与水平轴的处理完全对称，只是键位不同：

```csharp
public float MoveAxis  { get; private set; }   // D - A
public float DepthAxis { get; private set; }   // W - S
public Vector2 Axis2D => new Vector2(MoveAxis, DepthAxis);
```

冲刺有两个键（`dash` 左 Shift、`dashSecondary` 空格），在属性上合并成一个边沿：

```csharp
public bool DashPressed => _dashPressed || _dashSecondaryPressed;
```

两个键各自算边沿、再取「或」—— 这样同时按住 Shift 与空格也不会在下一帧重复触发冲刺（冷却本身也拦着，但语义上更干净）。

瞄准是持续状态，不是边沿：

```csharp
public bool AimHeld { get; private set; }            // 右键按住
public Vector2 AimScreenPosition { get; private set; } // 鼠标屏幕坐标（像素）
```

`AimHeld` 每帧从 `InputBindings.ReadAim()` 取；`AimScreenPosition` 取 `Mouse.current.position.ReadValue()`。`ui.json` 的尺寸与它配合，见第 8.5 节。

### 调试覆盖

`PlayerInputReader` 上有 `useOverride / overrideMoveAxis / overrideDepthAxis / overrideAttackHeld / ...` 一组字段和 `SetOverride(...)` 方法，可以在没有真实输入时驱动角色（无人值守跑状态机流程用）。整段用 `#if UNITY_EDITOR || DEVELOPMENT_BUILD` 包住，发行版里 `OverrideEnabled` 恒为 false、`SetOverride` 是空操作。这是 `tools/serialized-number-allowlist.txt` 里唯一被允许出现在组件上的数值字段，理由是它不是手感数值。

## 7. 数值与规则

| 文件 | 字段 | 影响 |
| --- | --- | --- |
| `player.json` | `moveSpeed` | 左右移动速度 |
| | `moveSpeedY` | 纵深（上下）移动速度 |
| | `dashDistance` / `dashDuration` | 冲刺距离 / 时长（速度 = 距离 ÷ 时长） |
| | `dashCooldown` | 冲刺冷却（从**冲刺开始**计时，不是从结束） |
| | `moveDeadzone` | 输入死区，低于它视为「没有移动输入」 |
| | `meleeDamage` | 近战每次命中扣多少血 |
| | `meleeRange` | 近战判定盒的长度（朝正面伸出），高度与抬升按它的比例推导 |
| | `meleeHitDelay` | 从按下到判定生效的时间（会被夹到动画时长的 60% 以内） |
| | `aimMaxAngle` | 瞄准时相对水平的最大仰/俯角（度），准星超出就贴着这个角打；必须小于 90 |
| `input.json` | 9 个绑定 | 键位（`a`/`d`/`w`/`s`/`leftShift`/`space`/`f`/`leftButton`/`rightButton`）；`dashSecondary` 是第二个冲刺键，`aim` 是瞄准键 |
| `arena.json` | `minY` / `maxY` | 可行走的纵向范围，相对单块背景图高的比例（0..1）；横向不在这里，等于整张地图的宽度 |
| `camera.json` | `offset` / `smoothTime` / `lockY` | 相机偏移、跟随平滑、是否锁 Y |
| `ui.json` | `aimRingSize` / `aimDotSize` | 准星外圈与中心点的直径（像素，按 Canvas 1920×1080 参考分辨率） |
| `assets.json` | `spine.animations.*`、`spine.muzzleBone` | 动画名、枪口骨骼名 |

**冲刺冷却放在 `PlayerController` 而不是状态里**：

```csharp
// PlayerController.Update()
_dashCooldown.Tick(Time.deltaTime);
```

- 冷却要跨状态有效：冲刺结束后进 Idle/Move，计时必须继续走。放在 `PlayerDashState` 里，退出状态就断了。
- `DashCooldown` 本身是 `Core/Rules` 下的纯 C# 类（`Configure / Start / Reset / Tick`，`IsReady => _remaining <= 0f`），不引用 UnityEngine，可以脱离引擎测试。
- 计时用**真实时间**而不是物理时间：冲刺冷却不该受 `timeScale` 或物理帧率影响。

**纵向范围为什么进 JSON、横向为什么不进**：

- 纵向：角色被夹在一幅插画上的带状区域里，边界是「画面上的位置」，不是关卡几何；画一换、缩放一改，世界坐标就得重新量，而比例不会变。`ArenaBounds` 挂在背景对象上，背景挪动/缩放，带子自动跟着走。
- 横向：它就是「这一关有多宽」。写进 JSON 或者存成场景里的数组，都会在加地图之后变成硬上限（新加的块不在数组里，玩家被卡在旧边界）；所以横向直接取所有背景块的并集，加一块就自动变长。
- 代价：横向不能单独收窄。真要在两端加墙，再补一个「墙」的碰撞体或另一个约束，而不是回头改这张表。

`PlayerController` 还集中了几个「所有状态都要用」的查询：`HasMoveInput`（读死区、按二维长度判断）、`CanDash`、`DashSpeed`、`Facing`、`Arena`。状态只读这些，不各自实现一遍，避免同一概念两套算法。

`HasMoveInput` 用二维长度而不是只看水平轴，是因为**上下走也算在移动**：否则按住 `W` 时角色会一路走一路被判定成「没有移动输入」，在 Idle/Move 之间来回切、动画不停重播。

## 8. 几个容易被问到的实现选择

### 8.1 为什么活动范围在 `FixedUpdate` 末尾统一夹，而不是各状态自己判

```csharp
private void FixedUpdate()
{
    _machine.FixedTick();
    ClampToArena();     // 状态机算完速度后统一夹一次
}
```

- 五个状态里每个都写一遍 `if (超出) 夹回来`，一定会有一处漏写或顺序写错（比如先夹后加速，速度又把角色推出去）；
- 夹在状态机后面，**任何状态**（包括以后新加的状态）都自动受约束，新增动作不需要记得处理边界；
- 撞到边界时不许再往外推，否则角色会贴着边界持续「顶墙」、动画还在播 Move。

夹取**不改位置，只削速度**：

```csharp
// 这一步允许的位移最多是「到边界的剩余距离」，速度超了就削到刚好抵达
if (velocity.x > 0f) velocity.x = Mathf.Min(velocity.x, (area.max.x - position.x) / dt);
```

先冲出去一点、再被瞬移回边界，是贴边抖动的根源：刚体开着插值，渲染位置在「边界」和「边界外一点」之间每物理帧来回插，看着就是抖。削速度让位置永远停在边界上、一次也不写回，插值没有「倒退」可言。位置只在真出现在外侧（冲刺、传送、场景初始摆放）时纠正一次。

读位置用 `body.position` 而不是 `transform.position`：`Rigidbody2D` 开启插值后，`transform` 是渲染用的插值位置，拿它做物理修正会与真实位置打架。

### 8.2 转身为什么只翻视觉根节点

```csharp
var scale = visualRoot.localScale;
scale.x = Mathf.Abs(scale.x) * direction;
visualRoot.localScale = scale;
```

翻 `Animation` 的 transform，不动胶囊碰撞体、不动 `Rigidbody2D`。翻碰撞体会让胶囊偏移方向跟着变，撞墙瞬间被弹开；翻刚体更糟，物理接触点全乱。视觉与碰撞分家是 2D 角色转身的标准做法。

### 8.3 为什么「开火」要广播事件而不是自己闪火光

```csharp
Fired?.Invoke(Facing, special ? bullet.ShotColor : Color.white);
```

控制器只声明「刚刚打了一发、朝向是哪边、这一发什么颜色」，**不碰 `SpriteFlash`**。枪口火光由 `MuzzlePoint` 订阅 `Fired` 自己播。这样加音效、加手柄震动、加弹壳，都只是「再加一个订阅者」，开火逻辑一行都不用改（`AGENTS.md` 硬约定第 11 条）。

### 8.4 相机交给 Cinemachine，控制器不碰它

跟随由场景里的 Cinemachine 虚拟相机（`Framing Transposer`，相机距离 10、跟随并注视 `Player`）负责，`PlayerController` 里没有任何相机代码。

好处是移动逻辑与取景彻底分开：`W/S` 只改角色自己的位置，镜头怎么跟、跟多近、要不要加噪声，全在虚拟相机上调。

**代价**：虚拟相机默认 X/Y 都跟，所以上下走时整幅背景会跟着平移（背景是静态插画，看着像镜头在飘）。如果要固定画面，把虚拟相机的 `Follow` 换成一个「只复制玩家 X」的空物体即可——这是场景配置，不用改代码。`Assets/Scripts/Game/Camera/CameraFollow2D.cs` 是早期没接 Cinemachine 时的跟随脚本，现在场景里没有挂它。

### 8.5 瞄准：屏幕点怎么变成子弹方向

按住瞄准键时，开火方向不是「面朝哪打哪」，而是「准星指哪打哪」：

```csharp
var depth = Mathf.Abs(camera.transform.position.z - from.z);   // 相机到枪口所在平面的距离
var world = camera.ScreenToWorldPoint(new Vector3(screen.x, screen.y, depth));
var delta = (Vector2)(world - from);
```

然后把这个方向收进「玩家面向一侧的扇形」里（`PlayerController.TryGetAimDirection`）：

```csharp
var side = delta.x >= 0f ? 1f : -1f;                       // 准星在哪一侧
if (Mathf.Abs(delta.x) < 0.0001f) side = Facing >= 0 ? 1f : -1f;   // 正在头顶时沿用当前朝向
var elevation = Mathf.Atan2(delta.y, Mathf.Abs(delta.x)) * Mathf.Rad2Deg;
elevation = Mathf.Clamp(elevation, -maxAngle, maxAngle);   // maxAngle = aimMaxAngle（<90）
var radians = elevation * Mathf.Deg2Rad;
direction = new Vector2(Mathf.Cos(radians) * side, Mathf.Sin(radians));
```

四件事值得记：

- **深度取相机到枪口的 z 差**，不是固定常数。正交相机下这样得到的点正好落在角色所在平面上，准星看着指哪儿、子弹就打哪儿。
- **方向与朝向脱钩**：`Facing` 只决定身体朝哪边站，不决定子弹去哪。开火时顺带把朝向翻到准星那一侧，避免「背对着人开枪」的观感。
- **角度被夹在 `aimMaxAngle` 内**：仰角/俯角绝对值不超过它（默认 55°），准星移到头顶时方向贴着上限打，不会朝正上方开枪。夹的是角度而不是「超了就退平射」——退回平射会让方向在越界那一帧突然跳变。
- **没有相机/枪口、或准星与枪口重合时退回平射**（`TryGetAimDirection` 返回 false）。这保证在没有鼠标的设备上按扳机仍是老行为，不会射出零向量。

准星本身是纯 UI：`Game/UI/AimReticleView.cs` 每帧读 `AimHeld` 与 `AimScreenPosition`，把 `root.anchoredPosition` 设成鼠标位置，尺寸取 `ui.json` 的 `aimRingSize`/`aimDotSize`。它不参与判定，也不反算世界坐标——那是 `PlayerController.TryGetAimDirection` 的事。两者都从 `PlayerInputReader.AimScreenPosition` 读同一份数据，不会出现「准星在这儿、子弹往那儿」。

画布与两张白图（圆环、圆点）由菜单 `ZeroWalker/生成瞄准准星 UI（UGUI）` 生成：Canvas 用 Screen Space - Overlay（永远贴屏幕、不受相机影响），`Image.raycastTarget = false`（不挡点击）。

### 8.6 2.5D 走位为什么把碰撞体设成 trigger

角色已经被活动范围约束，不需要和靶子做实体碰撞；开 `isTrigger` 后，玩家不会被靶子挡住而卡在斜向走位里，子弹的 `OnTriggerEnter2D` 判定照常工作。

## 10. 已知限制

- **没有重力、没有跳跃**：`W/S` 是纵深不是高度；`PlayerController` 里没有 `Grounded` 相关代码。
- **斜向比直向快**：两轴速度分别计算后相加，没有归一化（见 4.2）。
- **活动范围纵向是矩形**：`arena.json` 两个比例算出来的是一刀平的带子，不能贴合画面透视做梯形；画面上是斜的，边界会有几像素误差。横向铺满整张地图，没有左右墙。
- **地图靠命名约定自动收集**：只有名字以 `BG` 开头的 SpriteRenderer 会被当成地图（或都塞进 `ArenaBounds` 的 `root` 下）。起错名字不会报错，只是那块不参与范围计算。
- **冲刺用 `Move` 动画**：Spine 资源里没有对应动作，不是代码没写。
- **近战是身前一个矩形盒子**：一次挥击只判定一次，没有多段判定、没有连击、没有击退；盒子高与抬升由 `meleeRange` 按比例推导，不能单独调形状。
- **没有受击/死亡**：玩家不会被打断，也没有生命值。
- **移动端不可玩**：只有键鼠绑定；触屏需要虚拟摇杆与开火按钮，属新功能，待拍板。
